# Architectural & Implementation Deviations Register

This document records any variance between the implementation and the text of `NPRJ740_Final_Project_Report_v4.pdf`, along with rationale and resolution. Report v5 absorbs DEV-05 and DEV-07 to DEV-16, so they are no longer differences from the current report.

| ID | Topic | Report Statement | Implementation Choice | Rationale |
|---|---|---|---|---|
| DEV-01 | Python Runtime Version in Local Dev | Section 5.2 / 5.8 specifies Python 3.12 LTS. | Local development environment utilizes installed Python 3.14.5; Docker containers in Phase 9 pin Python 3.12 LTS (`python:3.12-slim`). | User requested to use pre-installed host Python 3.14 for local developer loop to avoid redundant installations. Containers adhere strictly to Python 3.12 LTS. |
| DEV-02 | Developer Loop Reverse Proxy | Section 5.8 specifies Nginx reverse proxy routing traffic on port 8080. | Local dev runs Vite dev server with proxy forwarding `/api` to native Django on port 8000. Full Nginx container stack on port 8080 delivered in Phase 9 via `deploy/nginx/` and `docker-compose.yml`. | Provides fast HMR during development while preserving single-origin cookie/CSRF semantics. Production stack verified on port 8080. |
| DEV-03 | Database Port Exposure in Development | Section 5.8 specifies database publishes no port to the host. | `docker-compose.dev.yml` maps port 5432 to host localhost for dev loop. Full deployment stack `docker-compose.yml` leaves database on internal network only with zero published host ports. | Required for native Django dev server to communicate with the PostgreSQL container; production container stack is completely isolated. |
| DEV-04 | Dedicated Development Compose Configuration | Section 6.1 specifies single `docker-compose.yml`. | Separate `docker-compose.dev.yml` runs PostgreSQL standalone for development, with `docker-compose.yml` providing the full four-container production stack (proxy, api, db, migrate). | Isolates dev service management from full production multi-container orchestration. |
| DEV-05 | Moroka Hall Room Data & Layout | Brief / initial assumptions estimated Blocks A-C across floors 1-3. | Institutional master data (`Everyone .xlsx`) contains 414 rooms across Block A (floors 2-3) and Block B (floors 0-4), plus standard common areas across all floors. | Accurately models real-world Sol Plaatje University campus facilities. |
| DEV-06 | Legacy Peer Deps for openapi-typescript | Report specifies TypeScript client type generation from OpenAPI 3.0 schema. | `openapi-typescript` installed with `--legacy-peer-deps` due to upstream tool declaring peer dependency on `typescript@^5.x` while project uses `typescript@~6.0.2`. | Types generate cleanly into `frontend/src/api/schema.d.ts` without runtime impact. |
| DEV-07 | Warden fault reports | BR-04 and AC-05.4: Wardens have no write capability; only a Resident submits. | A Warden may submit a fault for a location in their own residence and answer clarification questions on reports they filed. Every other write returns 403. | A Resident who cannot reach their account can still get a fault reported. The Warden is recorded as the reporter, so no resident identity is exposed. |
| DEV-08 | Room scoping | BR-09: a Resident reports against active Locations in their own residence. | A Resident reports only against their assigned room and common areas. `users.assigned_location_id` is an added column. | A student should not report faults in another student's room. |
| DEV-09 | CSV import columns | FR-04 lists email, full_name, role, residence, student_number. | Those columns plus an optional `room`. A blank role means RESIDENT and a blank residence means the active residence. | Without a room, an imported Resident could report only common areas (DEV-08). |
| DEV-10 | API paths | Section 6.3 lists paths such as `/api/users/import`, `/api/requests/{id}/transitions` and `/events`, with deactivate and reactivate as separate endpoints. | `/api/users/import-csv/`, `/api/requests/{id}/transition/` and `/timeline/`, `PATCH /api/users/{id}/` for active status, plus `/api/residences/`. List endpoints use trailing slashes. `docs/openapi.yaml` is the current list. | Follows Django URL conventions. The report table should be regenerated from the schema. |
| DEV-11 | List response shape | Pagination capped at 50 (Section 5.7). | Lists return `{total_count, limit, offset, results}`; request lists add `status_totals` so screens can show counts across all pages. | Screen counters must not be limited to the visible page. |
| DEV-12 | Code layout | Section 6.1 lists `backend/apps/reporting/` and `frontend/src/features/`. | `ReportingService` is in `apps/workflow/services.py`; screens are in `frontend/src/pages/`. | The reporting code is one service over workflow tables. |
| DEV-13 | Data dictionary additions | Table 5.7. | `transition_rules` stores Table 5.1. `audit_logs.request_id` and `work_order_id` are plain bigints rather than foreign keys. | Audit rows must outlive and stay independent of the records they describe. |
| DEV-14 | Body size limit | Section 5.7: request bodies 1 MB, CSV 2 MB. | nginx applies one 2 MB limit to all requests. | One limit keeps the proxy configuration simple; the CSV limit is what needs 2 MB. |
| DEV-15 | Historic MFA audit rows | Table 5.5 has no MFA actions. | Two-factor sign-in was built and then removed (Section 3.3 excludes it). Audit rows written while it existed are kept, so the `check_audit_action` constraint is `NOT VALID`: it binds every new row but does not rewrite history. | `audit_logs` is append-only. |
| DEV-16 | Generated client types | Section 5.2: API types are generated from the OpenAPI schema. | `frontend/src/api/schema.d.ts` is generated, but the screens use the hand-written types in `frontend/src/types/`. TLS and HSTS are also not included, because the assessed profile is HTTP on localhost. | The hand-written types came first and match the API. No screen depends on the generated file. |
